# spec.md — macOS Memory Explosion (Round 2): Plan-Level Pytest

## Overview
A second ~91 GB memory event occurred on 2026-04-12 while running
`/kamma:2-do @kamma/threads/20260412_vib_rule_workflow/`.
The previous fix (disabling pytest in `~/.claude/hooks/pytest_on_edit.sh`)
is still in place and working — the hook is NOT the culprit this time.

## Root Cause (Updated)

### Immediate cause
`kamma/threads/20260412_vib_rule_workflow/plan.md` explicitly calls
`uv run pytest --tb=short -q` (full test suite) in four tasks:
- Task 1.4: regression check
- Phase 1 Completion verification
- Phase 3 Completion verification
- Task 4.2: final quality gate

The kamma:2-do agent uses parallel Bash tool calls. This spawned three
concurrent full-suite pytest processes, confirmed live via `ps`:

| PID   | RSS      | Command                                      |
|-------|----------|----------------------------------------------|
| 75993 | ~1.6 GB  | pytest --tb=short -q                         |
| 76546 | ~1.7 GB  | pytest --tb=short -q (tail -20)              |
| 77067 | ~1.5 GB  | pytest --tb=short -q --ignore=test_vib...    |

All three are children of Claude PID 58688 (the other iTerm2 tab).

### Systemic cause
`kamma/workflow.md` line 52 mandates bare `uv run pytest --tb=short -q`
in the Quality Gates checklist. Every plan generated by `/kamma:1-plan`
inherits this call verbatim into every Phase Completion block. The plan
template is the root of the pattern.

### Why "91 GB"
Each pytest process allocates ~474 GB virtual address space (macOS maps
the entire venv into virtual memory via mmap). Activity Monitor's
"Memory" / "VM Size" column sums virtual address space across the
iTerm2 process group tree. With 3 pytest processes × 474 GB each, the
displayed figure is ~1.4 TB virtual. Physical RAM impact is ~5 GB per
set, but the virtual pressure causes macOS to swap aggressively.

## What needs to change

1. **`~/.claude/hooks/guard_pytest.sh`** (NEW) — PreToolUse hook script that
   inspects every Bash tool call and hard-blocks any `pytest` invocation that
   does not include a specific `tests/*.py` file path. Exits with code 2 +
   JSON block decision so Claude Code refuses to execute the command.

2. **`~/.claude/settings.json`** — add a `PreToolUse` entry wiring the
   `guard_pytest.sh` hook to the `Bash` tool matcher.

3. **`kamma/workflow.md`** — replace bare `uv run pytest --tb=short -q` in
   the Quality Gates with the targeted form and add a prohibition note. This
   is documentation-level reinforcement (Option C) on top of the hook.

4. **`kamma/threads/20260412_vib_rule_workflow/plan.md`** — replace all four
   bare pytest calls with `uv run pytest tests/test_vib_rule_workflow.py -v`.
   Edit ONLY after the currently running kamma:2-do session has finished.

5. **`~/.claude/hooks/pytest_on_edit.sh`** — verify pytest line remains
   commented out (confirmation step only).

## Affected files
- `~/.claude/hooks/guard_pytest.sh` (new file)
- `~/.claude/settings.json` (add PreToolUse block)
- `kamma/workflow.md` (documentation fix)

- `~/.claude/hooks/pytest_on_edit.sh` (verify only)

## Constraints
- Do NOT edit `vib_rule_workflow/plan.md` while the other tab's kamma session
  is still active
- Do NOT change pyright behavior
- The guard hook must use `exit 2` (not `exit 1`) — Claude Code treats exit 2
  as a hard block signal

## How we'll know it's done
- Running `bash ~/.claude/hooks/guard_pytest.sh` with a bare pytest command
  as input prints the block decision and exits 2
- Running it with a targeted `tests/test_foo.py` call exits 0
- `~/.claude/settings.json` contains the PreToolUse entry
- `kamma/workflow.md` Quality Gates show the targeted form + prohibition note
- `vib_rule_workflow/plan.md` has no bare pytest calls
- A subsequent kamma:2-do session shows no concurrent pytest processes

## What's not included
- Fixing the vib_rule_workflow logic itself
- OS-level ulimit configuration
- Pyright configuration changes
